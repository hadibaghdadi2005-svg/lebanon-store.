## What's been fixed (chronological)
1. **Fake login → real auth.** Removed the old "type any email/phone, no password, instantly logged in" system (which let anyone impersonate any customer, including the admin). Replaced with real Supabase Auth (email + password). `isAdminUser()` now checks a verified session email against `ADMIN_EMAIL`.
2. **Row Level Security was wide open.** Every table (`customers`, `orders`, `products`, `settings`) had RLS "enabled" but every policy was `true` for everyone — meaning direct API calls (bypassing the site entirely) could read/write anything. Locked down to: customers/orders scoped to their owner or admin; products/settings publicly readable but admin-only writable; storage bucket admin-only writable.
3. **Cost & supplier-link data was leaking everywhere** — hardcoded in the page's visible JS source, fully public in the `products` table, and embedded in every customer's own order history. Fixed by: stripping cost/supplier data from the JS source entirely, splitting `products` into an admin-only base table + a `products_public` view (safe columns only), and adding a database trigger that snapshots real cost server-side into an admin-only `order_item_costs` table at order time (the customer's browser never has access to cost data at any point).
4. **Session didn't persist across refresh** (always dropped back to login) — fixed by restoring the Supabase session on page load.
5. **Deleted orders didn't disappear for the customer live** — their realtime subscription only listened for status *updates*, not *deletes*. Added the missing handler + set `orders` to `REPLICA IDENTITY FULL` (needed for the delete filter to actually work).
6. **Misc correctness bugs:** order numbers had a hardcoded year (now dynamic), category/"View all" links did nothing (now real filtering), the shipping-fee consent modal described fake $/kg pricing (now matches the real flat per-governorate fee).

25. **Diagnosed and fixed "products sometimes disappear when I add them, and don't show to customers automatically."** Two separate bugs in `index.html`. First: `submitNewProduct()` picked the new product's id as `max(local PRODUCTS array ids)+1`, but `goAdmin()` loads the admin's full product list from the DB asynchronously without blocking the UI — adding a product quickly after opening the admin panel could compute an id that collided with a row already in the DB but not yet reflected locally, and the `upsert` would then silently merge the new product's fields into that existing row instead of creating a separate one, making the older product look corrupted/gone. Fixed by cross-checking the real max id in the database right before picking one, and by making product creation `await` the DB write and only show the "Product added!" toast (and only leave the product in `PRODUCTS`) if it actually confirmed — previously a failed insert was only `console.error`'d and still showed success, so the product would just vanish again on the next reload with zero explanation. Second: the customer-facing product list was only ever loaded once, in `initApp()` — there was no realtime subscription or refresh for it at all, so anyone already browsing the site never saw a product an admin added later without a manual page reload. Added a quiet 60-second polling refresh (`_productsRefreshTimer`) that only re-renders on an actual product-count change and only while sitting on the plain home view with nothing focused, deliberately guarded the same way the billboard timer above is, since this codebase has a documented history of exactly this class of bug (a timer's `render()` call stomping an in-progress interaction).

38. **Fixed a serious pre-existing RLS bypass found while adding sizes** (unrelated to the feature, discovered when re-creating the view). `products_public` deliberately runs with `security_invoker` **off** so anonymous shoppers can read the catalogue even though `products` itself is admin-only under RLS (item 31). The problem was that `anon` and `authenticated` also held INSERT/UPDATE/DELETE/TRUNCATE grants on that view, and Postgres reported it as auto-updatable — so anyone holding the public anon key (which ships in the page source, by design) could have written to or **deleted rows from the real `products` table straight through the view**, bypassing RLS entirely. Confirmed by role-simulating `anon` and running a `DELETE` that was accepted. Fixed by migration `products_public_read_only_for_clients`, which revokes every write privilege from `anon`/`authenticated` and leaves only SELECT; re-verified afterwards that the same delete now fails with `42501: permission denied for view products_public` while anon still reads all rows. The app only ever SELECTs from this view — every admin write goes to `products` directly — so nothing in the site changed. **Worth checking whenever a view is added:** a `security_invoker=off` view is an RLS bypass by construction, so its client-role grants must be SELECT-only.
